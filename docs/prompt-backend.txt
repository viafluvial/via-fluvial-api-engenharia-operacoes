## 4. Escopo obrigatorio do MVP

### 4.1. Registry server-side

Implemente um registry configuravel por `application.yml` e variaveis de ambiente. Nao grave segredos no repositorio.

Cada servico deve possuir, no minimo:

- `key` estavel;
- nome;
- categoria/dominio;
- ambiente;
- enabled;
- direct base URL;
- gateway base URL;
- lista ordenada de candidatos de health;
- expected transport mode;
- timeout;
- tags;
- dependencias conhecidas.

Use defaults locais para as portas 18001-18019. Para DSV/HML/PRD, URLs devem vir de configuracao. Nao invente endpoints de producao ausentes; retorne `NOT_CONFIGURED`.

Nao reutilize como defaults server-side as URLs de producao hardcoded atualmente no registry do frontend. Em LOCAL, use localhost; nos demais ambientes, uma URL ausente deve permanecer ausente e resultar em `NOT_CONFIGURED`, evitando checks acidentais de PRD durante desenvolvimento.

Nao exponha no DTO publico:

- API keys;
- bearer tokens;
- senhas;
- client secrets;
- JDBC URLs completas;
- headers secretos;
- URL interna quando o perfil nao puder ve-la.

### 4.2. Health checks server-side

Implemente checks HTTP server-side para evitar CORS e evitar que o navegador conheca credenciais tecnicas.

Requisitos:

- use cliente HTTP moderno do Spring compativel com a versao escolhida;
- timeout de conexao e resposta configuravel;
- limite global de concorrencia;
- uma falha nao cancela checks dos demais servicos;
- nao siga redirects para destinos nao permitidos sem validacao;
- bloqueie SSRF: somente URLs do registry server-side podem ser consultadas;
- nao aceite URL arbitraria em requests publicos;
- propague ou gere `X-Correlation-Id`;
- nunca registre headers/segredos em logs;
- interprete payload Actuator `{ "status": "UP" }` quando presente;
- 401/403 deve ser `AUTH_REQUIRED` ou falha de configuracao, nunca `UP`;
- 404 em um candidato pode tentar o proximo candidato;
- timeout/conexao recusada devem ser diferenciados de HTTP 5xx;
- medir latencia monotonicamente;
- guardar checkedAt em UTC.

Estados publicos:

- `UP`;
- `DEGRADED`;
- `DOWN`;
- `UNKNOWN`;
- `DISABLED`;
- `NOT_CONFIGURED`;
- `AUTH_REQUIRED`, se mantido como estado; alternativamente use um `reasonCode` obrigatorio.

Execute checks por dois caminhos quando configurados:

- `GATEWAY`;
- `DIRECT`.

Produza diagnostico deterministico:

- ambos UP: `HEALTHY`;
- gateway DOWN e direto UP: `GATEWAY_FAILURE`;
- gateway UP e direto DOWN: `DIRECT_PATH_FAILURE`;
- ambos DOWN: `BACKEND_OR_NETWORK_FAILURE`;
- modo esperado diferente do informado pelo frontend: `ROUTE_MISMATCH`;
- sem configuracao suficiente: `NOT_CONFIGURED`.

Este diagnostico nao deve alterar roteamento nem acionar fallback.

### 4.3. Scheduler e execucao manual

- scheduler configuravel, default razoavel de 30 segundos em DSV;
- scheduler pode ser desabilitado por ambiente;
- impedir sobreposicao da mesma rodada;
- endpoint manual deve retornar identificador da rodada e resultado consistente;
- proteger execucao manual por autorizacao;
- evitar tempestade de requests;
- shutdown gracioso.

### 4.4. Persistencia e Flyway

Siga integralmente `contrato-operacional-para-migrations-seeds.txt`. Regras de bloqueio:

- Flyway e o unico mecanismo de evolucao estrutural;
- `spring.jpa.hibernate.ddl-auto=validate` em `application.yml` e em todos os profiles, sem `update`, `create` ou `create-drop`;
- migrations estruturais em `src/main/resources/db/migration`, na faixa `V001-V099`;
- uma responsabilidade estrutural por migration, uma tabela por arquivo e migration propria para funcao/trigger de `updated_at`;
- seeds DSV em `src/main/resources/db/seed/dsv`, na faixa `V101-V199`, um arquivo por tabela, idempotentes e LGPD-safe;
- nao usar prefixo `S` nem repeatable migration para seeds;
- DSV usa `classpath:db/migration,classpath:db/seed/dsv`; HML/PRD usam somente `classpath:db/migration`;
- migrations aplicadas sao imutaveis e alteracoes futuras sao incrementais;
- constraints, indices, integridade referencial e colunas `created_at`/`updated_at` devem refletir o dominio;
- disponibilize README e relatorio executavel de qualidade da massa, incluindo volume, distribuicao e validacoes temporais/documentais aplicaveis.

Crie modelos separados para configuracao logica e resultado historico. Como minimo:

- `service_component` ou registry persistido apenas se houver vantagem sobre config; nao duplique sem necessidade;
- `health_check_run`;
- `health_check_result`;
- `frontend_runtime_snapshot`;
- opcionalmente `operational_event` para eventos de mudanca de status.

O historico deve guardar somente dados tecnicos sanitizados:

- service key;
- environment;
- route type;
- status;
- reason code;
- HTTP status;
- latency ms;
- checked at;
- resumo de erro limitado e sem segredo;
- run id.

Implemente indices para consultas por ambiente, servico e tempo. Implemente retencao configuravel de dados detalhados, com default conservador (por exemplo, 7 ou 15 dias), sem cron destrutivo nao testado.

Atualize `shared-db/init/00-init-vfa-databases.sql` para criar database/schema de engenharia de forma idempotente. No compose dedicado, use o usuario `engenharia-operacoes_app`; no shared DB local, siga o usuario real do orquestrador raiz por override de ambiente, sem hardcode de credencial no codigo.

### 4.5. Snapshot do frontend

Crie contrato para o frontend informar sua configuracao efetiva sanitizada:

- application name;
- environment declarado;
- transport mode `BACKEND` ou `GATEWAY`;
- runtime config presente ou nao;
- build version/commit quando disponiveis;
- lista de service keys habilitadas;
- timestamp do cliente apenas informativo;
- timestamp do servidor autoritativo.

Use um request fechado equivalente a:

```json
{
  "application": "via-fluvial-app",
  "environment": "LOCAL",
  "transportMode": "BACKEND",
  "runtimeConfigPresent": true,
  "buildVersion": "1.0.0",
  "buildCommit": "abc1234",
  "enabledServiceKeys": ["viagens", "reservas", "pagamentos"],
  "clientTimestamp": "2026-08-08T19:00:00Z"
}
```

Enums, quantidade e tamanho das strings/lista devem ser validados. Campos desconhecidos devem ser ignorados ou rejeitados de modo consistente com a configuracao Jackson escolhida; em nenhum caso devem ser persistidos dinamicamente.

Nao aceite nem persista URL arbitraria, API key, token, cookie ou header. Use allowlist de campos e limite de tamanho. O snapshot nao controla roteamento; serve apenas para diagnostico.

## 7. Fallback e cores operacionais

Nao implemente fallback Gateway -> backend direto no navegador nem nesta API agregadora.

A API apenas reporta:

- rota esperada;
- rotas testadas;
- resultados;
- divergencia;
- estado de contingencia vindo de uma fonte/configuracao confiavel, se existir.

`FALLBACK_ACTIVE` somente pode aparecer se houver declaracao controlada de infraestrutura. Nao inferir que o trafego mudou apenas porque gateway falhou e direto respondeu.

Nunca recomendar fallback para 400, 401, 403, 404, validacao ou erro de negocio. Falhas candidatas a contingencia se limitam a timeout, conexao, DNS e 502/503/504, mas a ativacao fica fora deste MVP.
